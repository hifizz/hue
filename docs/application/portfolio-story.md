# 作品集主线故事：Agent 被杀掉之后，你还知道它做过什么吗

这份文档回答三件事：core 里最值得讲的东西是什么，证据在哪里，怎么把它讲成一条线。

- 代码引用写于 2026-11-06，行号会漂移，以函数名为准。
- 标 **[待你补]** 的地方是只有你知道的真实经历，我不替你编。
- 标 `TODO(verify)` 的地方是对其他 harness 的说法，我没有核实过。

---

## 一句话

**一个会改变外部世界的 agent，必须在任何时刻被杀掉之后，都能回答「我刚才做到哪了」。**

core 用三个很小的设计回答这个问题：

1. 写前日志：`tool.call` 一定先落盘，工具才开始执行。
2. 事件日志是唯一事实源：状态不存第二份，永远从日志算出来。
3. 一个 `effects` 字段：同时决定并发调度、崩溃后怎么告诉模型、policy 拿到什么信息。

这三件事都不需要「能用」就能讲清楚，也都有可运行的证据。

---

## 1. 问题：只读工具时它不存在，有了副作用就躲不掉

一个只会读文件、搜网页的 agent，进程被杀了，重来一遍就行。

工具开始产生副作用（发邮件、删文件、付款、`git push`）之后，进程在工具执行中途被杀，重启时有三种可能，而你分不清是哪一种：

| 状态 | 邮件发出了吗 | 日志里有什么 |
|---|---|---|
| 还没开始 | 没有 | 什么都没有 |
| 已经完成 | 发了 | 看日志写在哪个时刻 |
| 执行到一半 | 不知道 | 看日志写在哪个时刻 |

所以问题的核心是**顺序**：日志写在副作用之前还是之后。写在之后，执行和落盘之间的那个窗口里发生的事没有任何记录。这是数据库里的写前日志（WAL）要解决的问题，也是支付系统里幂等性分级要解决的问题。agent 只是把同一个老问题重新带到了一个新地方。

---

## 2. 三个设计，各自的机制、证据、代价

### 2.1 写前日志：用 generator 的「拉」换来持久化顺序

**机制。** `runTurn()` 是 async generator。消费者每调一次 `next()`，loop 才往前走一步。在 `loop.ts` 的 `executeCalls` 里（写作时是第 196 到 198 行），一个批次里所有 `tool.call` 先全部 `yield`，之后才启动工具。消费者只要遵守「落盘之后再 `next()`」，就保证了 `tool.call` 在工具执行前已经写进日志。

core 自己不碰 I/O，却拿到了持久化顺序的保证。靠的是「拉取式」这个控制流，而不是调用存储。

**和 AI SDK 的对照（读 ai@7.0.83 的源码得出，没有运行验证）。** AI SDK 有 `onToolExecutionStart` 回调，在工具执行前调用（`execute-tool-call.ts`）。但回调是通过 `util/notify.ts` 调的，它把每个回调包在 `try { await callback() } catch {}` 里，注释写明 *"Errors in callbacks do not break the generation flow"*。所以在这个回调里写日志，写失败时工具照样执行。

这是观察者式回调的合理设计：监控代码出错不应该拖垮用户请求。但它意味着回调不能当写前日志用，要做 WAL 得自己包一层 `execute`。两种设计服务的目标不同，不是谁对谁错。Pi、Mastra、Claude Code 怎么处理 `TODO(verify)`。

**证据。** `hue/packages/core/test/crash-sweep.test.ts`：

- 脚本固定产生 12 个事件。测试在每个事件上各杀一次，共 24 个杀点：
  - `afterPersist`：事件已落盘，在拉下一个之前被杀
  - `beforePersist`：事件到了消费者手里，但磁盘写入之前被杀
- 每个杀点都检查同一条不变量：**只要外部世界里邮件发出过，日志里就一定已经有对应的 `tool.call`**。
- 每个杀点之后还检查：用 `repairDangling` 修复后，没有悬空调用，没有未结束的 turn，历史对 provider 合法。
- 另有一个测试：存储写 `tool.call` 失败时，消费者不再拉取，邮件**没有发出**。

**这个测试有效吗？我做了变异实验。** 把 `loop.ts` 里「先 yield `tool.call`」和「启动工具」两行对调，再跑测试：

| 测试 | 变异后 |
|---|---|
| 原有的 `write-ahead` 测试 | 失败 |
| 存储写失败测试 | 失败 |
| 扫描测试，`beforePersist@5` | 失败，信息是「邮件已发出，但日志里没有 tool.call」 |

还原后全部通过，我用 `diff` 确认 `src/loop.ts` 与改动前逐字节一致。

这里有一个值得写进故事的细节：**我的第一版扫描只有 `afterPersist` 一种杀法，变异之后依然全绿。** 也就是说第一版测试对它声称要保护的东西没有保护力。加上 `beforePersist` 之后才抓住。一个只验证「正常路径没出错」的测试，在这类问题上等于没写。

**代价。**

- 保证是一个**协议**，不是类型约束。core 无法强制消费者「先落盘再拉」，忘了就失效。缓解办法是把驱动循环的代码集中在 `@hue/runtime` 一处，并用 `EventStore` 合同测试约束存储。
- 每个批次多一次落盘等待。
- 流式增量（`model.delta`）不落盘，所以流式中途崩溃只能保留已完成的消息。

### 2.2 事件日志是唯一事实源：不存第二份状态

**机制。** `ConversationState` 是 `fold(events)` 的纯函数结果（`fold.ts` 的 `reduce`）。loop 自己维护状态的方式，就是对自己发出的每个持久化事件调用同一个 `reduce`（`loop.ts` 第 75 行）。所以 turn 结束时的内存状态，和从日志重新 `fold` 出来的状态，**逐字段相等**，不是「应该相等」。

**为什么这一点重要。** 「内存状态和磁盘状态不一致」是一整类 bug，这里根本没有第二份状态，所以这类 bug 不存在。恢复、回放、分支、eval 归因都退化成「读日志」这一件事。

崩溃后的悬空调用也是这样算出来的（`fold.ts` 第 54 到 64 行）：`model.message` 里每个 tool-call 先登记为悬空，`tool.call` 补上 `effects`，`tool.result` 把它移除。日志停在哪，`danglingCalls` 就停在哪。

**证据。** `loop.test.ts` 的第一个测试断言 `fold('s1', 持久化事件) 深度相等 result.state`。`crash-sweep` 里每个杀点都是「只用日志重建」。

**代价。**

- 日志只增不减，需要压缩和归档策略。
- 消息格式变了，要在 `fold` 里兼容旧事件，靠事件上的 `v` 字段。
- 设计上必须明确哪些事件不落盘（`model.delta`、`tool.input.delta`、`tool.progress`），由 `isDurable()` 一个函数决定。

### 2.3 一个 `effects` 字段：读它的有几处，各自做什么

`Effects = 'none' | 'idempotent' | 'unsafe'`（`tool.ts` 第 12 行）。

| 谁在读它 | 做什么 | 位置 |
|---|---|---|
| 调度 | 连续的 `none` 合成一批并发，其他串行 | `loop.ts` 第 183 到 185 行 |
| 崩溃恢复 | `none` 的悬空调用告诉模型「可以安全地再调一次」，其他告诉模型「结果未知，先检查状态再重试」 | `recover.ts` 第 15 到 17 行 |
| policy | `PolicyCall.effects` 作为入参交给 `PolicyPort.decide` | `ports.ts` |

**说清楚的边界。** 第三处只是把信息交给 policy，默认策略（读放行、写要问）不在 core 里，由 `@hue/policy` 决定。所以准确的说法是「core 里有两处直接读它，第三处是把它交给策略」，不是「它直接驱动三件事」。

**一个值得讲的点：恢复文案是写给模型读的。** `recover.ts` 补进历史的那条合成结果，最终会被模型读到。「Its outcome is unknown; check the current state before retrying」这句话，决定了模型下一步是盲目重试，还是先去检查邮件箱。这是对模型行为的设计，不只是工程细节。

**风险与代价。**

- 标签由工具作者负责。把有副作用的工具标成 `none`，才是危险的方向，会被并发执行，崩溃后还被告知「可以安全重试」。反方向（把读标成 `unsafe`）只损失并发和自动化。拿不准时标 `unsafe`。
- `toolContract` 只验证 `effects` 的取值合法，**验证不了标得对不对**。
- 目前崩溃后**不自动重跑**任何调用，哪怕是 `none`。这是 `docs/packages/core.md` 里的 `TODO(deep)`。后果是模型得自己重新调用。

## 3. 杀点扫描里看到了什么

下面是探索阶段对 `afterPersist` 模式打印的结果（脚本：第 1 步并行请求 `send_email`（unsafe）和 `read`（none），第 2 步收尾）。提交的测试断言的是不变量，不打印这张表，所以这张表是示意，不能从仓库直接复现。

| 杀在 | 外部世界 | 日志里有 `tool.call` | 恢复时发现的悬空调用 |
|---|---|---|---|
| 第 3 个事件后（`step.started`） | 邮件未发 | 否 | 无 |
| 第 4 个事件后（`model.message`） | 邮件未发 | 否 | c1（effects 未知），c2（effects 未知） |
| 第 5 个事件后（`tool.call` c1） | 邮件**未发** | 是 | c1（unsafe），c2（effects 未知） |
| 第 6 个事件后（`tool.result` c1） | 邮件已发 | 是 | c2（effects 未知） |
| 第 7 个事件后（`tool.call` c2） | 邮件已发 | 是 | c2（none） |

从第 5 行能看出保证的**方向**：日志里有 `tool.call`，不代表事情发生了。那一刻邮件其实还没发。恢复流程只能说「可能发生过，结果未知」，保守处理。这也是为什么保证是单向的：**副作用发生过 ⇒ 日志里一定有记录**，反过来不成立。

另一个测试专门构造「邮件已发出，`tool.call` 已落盘，`tool.result` 没来得及落盘」这个最危险的窗口：恢复后 `c1` 被标为 `synthetic: 'crashed'`，文案是「outcome is unknown」，接着跑下一个 turn，邮件**没有被重发**，模型看到了「结果未知」。

## 4. 这个故事不能声称的

面试官追问时，下面这些要主动说，比被问出来好：

- **杀点是模拟的。** 「杀进程」是消费者不再拉 generator，不是真实的 `SIGKILL`。真实的 `kill -9` 加 SQLite 的测试是 `docs/tasks/wave-1/04-store.md` 的任务，还没做。
- **保证是单向的，不是「恰好一次」。** 它保证不丢失「发起过」这个事实，不保证知道结果。
- **工具内部的多步副作用，core 管不了。** 一个工具内部先发邮件再写数据库，在中间被杀，core 只知道「这个调用结果未知」。要靠工具自己设计成幂等。
- **依赖消费者纪律。** 见 2.1 的代价。
- **没有和其他 harness 对照。** 其他实现怎么处理崩溃恢复，我没核实。
- **崩溃后不自动重跑**，哪怕是纯读调用。

## 5. 怎么把它讲成一个大故事

现有的长文大纲（`docs/01-why-article-outline.md`）第 1 节是「我在 harness 之上踩过的坑」，第 3 节是「Hue 是什么」。这条主线可以同时撑起这两节，把「踩坑」和「设计」接成一个因果链。

**四拍结构：**

1. **事故。** 一个真实的、具体的事故：agent 在做一件有副作用的事时被中断，重启后你分不清它做没做。**[待你补]** 这应该来自 TARS 或 ThreadChat 的真实经历。大纲里已经有一条 `TODO(deep)`：挑 2 个最有说服力的事故，写成「现象 → 原因在哪一层 → 当时没法改」。我不知道你遇到过什么，所以不替你写。
2. **老问题。** 这不是 agent 才有的问题，数据库叫写前日志，支付系统叫幂等和对账。当工具开始有副作用，agent 就进入了分布式系统的世界。
3. **三个小设计。** 对应第 2 节：先落盘再执行，状态只从日志算，一个字段区分副作用。每个设计配一个可运行的测试，加一个我自己的测试曾经没抓住 bug 的坦白。
4. **诚实的边界。** 对应第 4 节。「我能保证什么，不能保证什么」比一个漂亮的断言更让人信任。

**为什么这条线适合求职：**

- 它对应 `docs/00-goal.md` JD 对照表里的「内核」和「对模型行为有品味」两行，后者的证据是 `recover.ts` 里写给模型读的恢复文案。
- 它能被**验证**，不是观点。读者跑一条命令就能看到 24 个杀点。
- 它符合大纲的写作原则：不说「更好」，说「我选了 X，代价是 Y」。
- 它回答了 `docs/04-challenges.md` 里的面试追问 1 和 10（async generator；崩溃后怎么恢复）。追问 2（并行工具里一个失败怎么办）这条故事没有覆盖。

## 6. 面试追问与短答

**为什么 loop 用 async generator？**
消费者拉一次它才走一步，天然背压；更重要的是，「落盘之后再拉」让 core 不碰 I/O 也能保证 `tool.call` 先于工具执行落盘。

**为什么不在回调里写日志？**
我核实过 AI SDK 7.0.83：回调异常会被吞掉，写失败时工具照样执行。回调适合观察，不适合做写前日志。

**你怎么知道这个保证真的成立？**
24 个杀点的扫描，加变异实验：把顺序对调后，扫描和原有测试都变红。顺带一提，我的第一版扫描在变异后依然全绿，是因为只在落盘之后杀，后来补了落盘之前这种杀法。

**进程在工具执行中途崩溃，恢复时怎么办？**
`fold` 日志得到悬空调用，`repairDangling` 为每个补一条 `crashed` 结果，一律不重跑，文案按 `effects` 区分，交给模型判断。

**`effects` 标错了怎么办？**
标成更保守的 `unsafe` 总是安全的。标成 `none` 但实际有副作用才危险。合同测试只能验证取值合法，验证不了标得对不对，这是工具作者的责任，也是已知缺口。

**这个保证强在哪里，弱在哪里？**
强：副作用发生过，则日志里一定有记录。弱：不保证知道结果，不保证恰好一次，依赖消费者先落盘再拉。
