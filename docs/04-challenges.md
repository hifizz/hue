# Hue：重点、难点、挑战与越过方法

> v0.1，2026-10-29。配合 docs/ 骨架使用。目标不变：① 求职投递包 ② 最终把 Hue 写出来。

## 一句话判断

最大的风险不是技术，而是**范围和时间**：13 层很容易做成 13 个半成品。越过它的办法只有一个——先把 5 个重点做深，其余只写接口和设计。

---

## 一、重点：必须做好的 5 件事

面试官会从这 5 件事判断你懂不懂 harness，其余都是加分。

| # | 重点 | 为什么是重点 | 做到什么程度算"好" |
|---|---|---|---|
| 1 | **loop + 事件合同** | 所有包都靠它通信，定错了后面全返工 | 能讲清停止条件、并行工具、打断后历史里留什么 |
| 2 | **手写 MCP client** | JD 明确要"懂调用链路底层" | 按 2026-07-28 无状态规范，不依赖官方 SDK，兼容 2025-11-25 server，有协议级测试 |
| 3 | **context 压缩** | 长任务能不能跑完的分水岭，也是各家差异最大的地方 | 三种策略 + eval 上的对比数据 |
| 4 | **eval 报告** | 证明"对模型行为有品味"，把观点变成数据 | 一条命令复现，含 3 个失败案例分析 |
| 5 | **长文 + 横评** | 让面试官在读代码之前就信你 | 每句对别家的描述都有源码或文档出处 |

skills、memory、子 agent 也要做，但做到"能用 + 讲得清取舍"即可。

## 二、技术难点

每一项按「为什么难 → 怎么越过 → 最低退路」写。

### 1. 事件合同：定早了会锁死，定晚了会乱

- **为什么难**：事件是跨包唯一通信方式。粒度太细，日志膨胀、回放复杂；太粗，telemetry 和 eval 拿不到需要的信息。子 agent 的事件树、副作用标注这些需求要到第 3 周才真正出现。
- **怎么越过**：
  - 第 1 周只定最小集合（turn.start / model.delta / model.message / tool.call / tool.result / turn.end），每个事件带 `v: 1`
  - 预留 `id` 和 `parentId` 字段，第 1 周不用也先放着，给子 agent 树留位置
  - 区分"可持久化"和"仅流式"事件（delta 默认不落盘）
  - 允许在第 3 周发一次 `v: 2`，并在 ADR 里写为什么改——这本身就是好的博客素材
- **最低退路**：事件合同只服务 runtime 和 eval 两个消费者，别为假想需求设计。

### 2. loop 的打断与并行工具调用

- **为什么难**：一轮里模型可能发出多个工具调用；用户随时可能打断或插话。要回答：并发还是串行？一个失败其他怎么办？打断时正在跑的 bash 怎么收尾？历史里留下什么才能让模型下一轮不困惑？
- **怎么越过**：
  - 全程用 AbortSignal 贯穿 loop → 工具 → 子进程
  - 规则先定简单版：只读工具可并发，有副作用的串行；打断后给每个未完成调用补一条 `tool.result(isError, "interrupted by user")`，保证历史里 call/result 成对
  - 用 mock ModelPort 写确定性测试覆盖：正常、并行、单个失败、中途打断、超时
- **最低退路**：求职版全串行，在 ADR 里写清楚并发的设计和没做的原因。

### 3. 手写 MCP client 的协议细节（按 2026-07-28 规范）

- **为什么难**：新规范把 MCP 变成了无状态——没有 initialize 握手，每个请求在 `_meta` 里自带版本和能力；新增必须实现的 `server/discover`；server 要更多输入时不再主动发请求，而是走 MRTR（返回 `input_required`，client 带 `inputResponses` 重发原请求）；Streamable HTTP 去掉了会话 ID 和 SSE 续传，断流只能用新 ID 重发。难点从"维护会话"变成了"每个请求都自洽 + 重发安全"。同时现实里大量 server 还是 2025-11-25 版，必须兼容。
- **怎么越过**：
  - 一个 `withMeta()` 包装所有请求，client 不持有协议会话状态
  - 连接后先调 `server/discover` 选版本；遇到 -32022 换版本重发一次
  - 所有 result 先看 `resultType`，缺省按 `complete`；MRTR 设重试上限，防止无限 `input_required`
  - 断流重发和工具的 `sideEffect` 标注联动：none/idempotent 自动重发，unsafe 交给模型判断
  - 老 server：discover 失败 → 回退到 initialize 流程，差异关在 `legacy.ts`，对上层同一个接口
  - 用官方 SDK 当对照答案，录 JSON-RPC 报文逐条比；再写一个故意出错的 mock server
  - 先只做 stdio + tools/list + tools/call；HTTP 第二步；subscriptions/listen、tasks extension、OAuth 全部 LATER；Roots/Sampling/Logging 已弃用，不做
- **最低退路**：stdio 下新规范 + 老 server 回退都能用，HTTP 只读跑通；博客讲清"无状态之后 client 少写了什么、多写了什么"。

### 4. 上下文压缩的质量看不见

- **为什么难**：摘要丢了关键信息不会报错，只会让 agent 在 20 轮后"变笨"。压缩还会打破 prompt cache 前缀，成本悄悄上升。
- **怎么越过**：
  - 每次压缩发 `context.compacted` 事件（前后 token、策略），让它可观测
  - 在 eval 里专门放 3–4 个"必须记住早期细节"的长任务，压缩质量直接变成成功率
  - 对比三种策略：截断 / 摘要 / 工具结果折叠；记录 token 与 cache 命中
  - token 计数先用近似（字符/4），在 ADR 里注明误差，后面再换 tokenizer
- **最低退路**：只做"工具结果折叠 + 摘要"两种，用一张对比图说话。

### 5. memory：写进去的是垃圾，召回的不是要的

- **为什么难**：模型主动 remember 时爱写废话；召回好不好很难量化；和 skills、context 的边界容易糊。
- **怎么越过**：
  - 形态先选 markdown 文件（可读、可编辑，符合 Hue 的"可读"承诺），不上向量库
  - 写入：只给 remember 工具 + 清晰的写入准则；召回：启动时注入摘要 + recall 工具按需查
  - 边界一句话写死：context 管"这一次喂什么"，memory 管"跨会话记什么"，skills 管"怎么做某类事"
  - eval 里放 2 个跨会话任务（第一次告诉偏好，第二次检查是否用上）
- **最低退路**：只做文件记忆 + 启动注入。TARS 的经验写进长文，代替复杂实现。

### 6. 子 agent 与编排

- **为什么难**：上下文隔离、结果回传格式、并发上限、事件树、递归 spawn、取消传播，每一个都能单独写一篇。
- **怎么越过**：
  - 子 agent 就是一个 Tool（task / spawn_agent），复用已有 loop，不发明新机制
  - 子 agent 的事件带 parentId 写入同一个 store，事件树自然就有了
  - 禁止递归（深度 1），并发上限 2–3
  - 插话先只做 queue（下一轮生效），steer 写设计不实现
- **最低退路**：串行子 agent + 结果摘要回传。

### 7. 崩溃恢复与副作用不重放

- **为什么难**：进程在工具执行中途被杀，重启后这个工具到底执行了没有？重放会不会再删一次文件？
- **怎么越过**：
  - 工具声明 `sideEffect: 'none' | 'idempotent' | 'unsafe'`（tools 接入规范的一部分）
  - 恢复时：只有 call 没有 result 的 unsafe 调用不重跑，补一条 "unknown, process crashed" 交给模型判断
  - 这正是 TARS 经验的用武之地，写成长文第 1 节的事故案例
- **最低退路**：求职版只支持"从最后一个完整 turn 恢复"。

### 8. eval 的公平性与可复现

- **为什么难**：模型输出不稳定；和 Pi 对比时 prompt、工具、模型版本稍有不同结论就不成立；任务太简单没区分度，太难都失败。
- **怎么越过**：
  - 评分以测试通过为主（客观），LLM judge 只做辅助
  - 每题跑 3 次取通过率；固定模型版本和温度；记录全部事件日志
  - 对照组只选 Pi（同模型），Claude Code 作可选
  - 先做 8 题跑通流程，再扩到 20 题
  - 失败案例比成功率更有价值：每个失败标注"发生在哪一层"
- **最低退路**：8 题 + 3 个失败案例分析，也足够支撑一篇报告。

### 9. "可读"承诺与功能之间的拉扯

- **为什么难**：每加一个边界情况，代码就长一点；"一下午读完"很快会失效。
- **怎么越过**：
  - 给每个包定行数预算（建议 ≤ 800 行，loop.ts ≤ 300 行），CI 里检查
  - 超出预算的东西拆成可选子路径，或者写进 ADR 不实现
- **最低退路**：README 里给出"30 分钟阅读路线"，即使代码长一点也能读。

## 三、非技术挑战

### 1. 范围蔓延（最大风险）
- **表现**：每层都想做完整，第 3 周还在写 sandbox。
- **越过**：严格按 03-roadmap 的求职版切片；任何新想法先写成 `LATER:` 标记；每周五检查一次范围。

### 2. 求职时间窗口
- **表现**：等 Hue 完美才投递，错过机会。
- **越过**：第 2 周末仓库可跑就开始投（附进行中的仓库 + 构建日志）；长文发出是第二波投递节点。

### 3. 用 AI 写代码，但面试会追问
- **表现**：ThreadChat 帮你写出来了，但你讲不清为什么这样写。
- **越过**：
  - 每个 DECIDE 都必须由你写 ADR 的"决定"和"代价"两段（可以让 AI 起草，但要自己改到能脱稿讲）
  - 核心文件（loop、MCP client、压缩）至少手动重写或逐行审一遍
  - 每周给自己做一次"5 分钟白板讲解"录音

### 4. 对别家的说法不准确
- **表现**：横评里一句错的描述，会让懂行的面试官怀疑全文。
- **越过**：所有 `TODO(verify)` 必须附源码行或文档链接才能删；源码克隆目录目前是空的，需要重新 clone；拿不准的就写"据文档"或删掉。

### 5. 深度探索时结论漂移
- **表现**：ThreadChat 里几轮探索下来，文档之间互相矛盾。
- **越过**：
  - 每轮只处理一个标记，产出 ADR + 对应文档的 diff
  - 02-architecture 是唯一事实源，改接口必须先改它
  - 文档放进 GitHub 仓库，结论以 PR 合并，历史可追

### 6. 写作和开发抢时间
- **越过**：边做边记"博客素材"段（每个包页底部已留），周末把素材串成构建日志；长文第 3 周集中写。

### 7. 品牌与命名
- Hue 容易和 Philips Hue 混淆：对外一律写 Hue Agent / hue.dev；@hue org 尽早确认能否注册，不行就备选 @hueagent。

## 四、面试可能追问（准备好答案）

1. 你的 loop 为什么用 async generator？背压和取消怎么处理？
2. 并行工具调用里一个失败了怎么办？
3. MCP 去掉握手、变成无状态之后，版本和能力怎么协商？`server/discover` 解决什么问题？版本不匹配（-32022）时你的 client 怎么做？
4. MRTR 是什么？为什么用"返回 input_required + 重发原请求"取代 server 主动发 sampling / elicitation 请求？对 loop 和打断有什么影响？
5. Streamable HTTP 没有会话 ID 和续传之后，断流怎么处理？有副作用的工具能自动重发吗？需要跨调用状态时怎么办？
6. 你怎么同时兼容 2026-07-28 和 2025-11-25 的 server？
7. 压缩什么时候触发？你怎么知道摘要没丢关键信息？对 prompt cache 有什么影响？
8. skills 和 memory 为什么分开？各自的边界在哪？
9. 子 agent 的上下文怎么隔离？结果怎么回传？
10. 进程在工具执行中途崩溃，恢复时怎么办？
11. 你的 eval 和 Pi 对比公平吗？结论有多可靠？
12. 如果让你在 Claude Code 里加一个功能，你会加什么？为什么？
13. 13 层里你觉得哪一层最被低估？

每题的答案最终应该能在某份 ADR 或博客里找到。

## 五、每周检查点（不达标就砍范围）

| 时间 | 必须达成 | 不达标时砍什么 |
|---|---|---|
| 第 1 周末 | 编码 agent 在真实仓库修好一个 bug；MCP stdio 能用（新规范 + 老 server 回退） | 砍 MCP HTTP，ai 层直接用 AI SDK |
| 第 2 周末 | 压缩能跑长任务；skills、memory 最小可用；开始投递 | memory 只做启动注入；skills 只做索引 + 读文件 |
| 第 3 周末 | 子 agent 可用；eval ≥ 8 题出报告；长文发布 | 子 agent 只串行；横评缩到 3 家 |
