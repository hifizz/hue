# ADR-016 运行中插话（steer）在下一个安全点注入，不截断也不并发
- 状态：已接受（2026-11-12 回填，2026-11-12 经用户阅读确认）
- 包：@hue/runtime
- 来源标记：无 `DECIDE:`。出处 runtime DECISIONS 第 2、3 条

## 问题
agent 正在跑时用户又发话，怎么处理？同一个会话能并发 `run` 吗？

## 候选
1. 排队：等当前 turn 结束再处理。
2. 注入：在安全点作为 `user.message { steer: true }` 并入同一个 turn。
3. 截断：立刻打断正在输出的回复。

## 各家怎么做（附出处）

## 决定
- `steer()` 排进队列，在 core 约定的安全点（本步所有工具结果都齐了之后）注入同一个 turn。不截断正在输出的回复，也不在工具执行中间插入。理由：provider 要求 tool-call 和 tool-result 成对相邻，只有步与步之间安全。
- turn 结束的瞬间才到的插话：正常结束就接着开一个 turn；被打断 / 出错结束的，放进 `RunResult.undelivered` 还给调用方。
- 同一个会话不能并发 `run`，再 `run` 直接抛错（指向 `steer()`）。不同会话互不影响。
- 调用方中途放弃（`return()`）等于先打断、补齐日志，再释放会话。

## 代价
模型正在写大段回复或一个耗时 10 分钟的 bash 时，插话要等它结束才生效；想立刻生效用 `interrupt()` 再 `run()`。互斥只在同一个 `Agent` 对象内；两个进程同时打开同一个会话靠 store 的 `(sessionId, seq)` 主键兜底，**没有测过**。设计页里的"排队式"插话没做。

## 如何验证（eval / 测试）
runtime 测试覆盖：插话在安全点送达、turn 结束瞬间才到的插话、打断含排队中的、放弃 `run`、会话互斥。没有在真实模型上验证过。
