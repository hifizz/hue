# ADR-007 edit 工具用精确字符串替换
- 状态：已接受（2026-11-12 回填，2026-11-12 经用户阅读确认）
- 包：@hue/tools
- 来源标记：`DECIDE: 搜索替换 vs 行号 patch vs unified diff`（docs/packages/tools.md:12）；`DECIDE: edit 工具格式`（tools.md:29）

## 问题
模型怎么表达"改这个文件的这一处"？

## 候选
| | 精确字符串替换 | 行号 patch | unified diff |
|---|---|---|---|
| 模型要写什么 | 原文片段 + 新片段 | 起止行号 + 新内容 | 带上下文的 `@@` hunk |
| 最容易错在哪 | 缩进 / 空白不一致 | 行号：模型数不准，前一次编辑后行号全变 | hunk 头里的行数，上下文行抄错 |
| 失败时 | 明确："找到 0 处 / N 处" | 悄悄改错位置 | 整个 patch 被拒，错误难读 |
| 重放时 | 找不到原文 → 安全失败 | 改错位置 | 通常失败，但不总是 |

## 各家怎么做（附出处）
设计页说各家对比是好素材，但没有核实过 Claude Code / Pi 等的 edit 格式 `TODO(verify)`。

## 决定
选精确字符串替换（`old_string` / `new_string` / `replace_all`）。失败是响应式的、可读的、不会改坏文件；这也是它能标 `idempotent` 的依据（同一调用执行第二次会失败但文件不变）。
细节：0 处匹配时若去掉首尾空白能找到，提示检查缩进；CRLF 文件用 LF 的 `old_string` 也能匹配并还原 CRLF；用 `split/join` 而不是 `String.replace`，避免 `$&` 被当成替换模式；非 UTF-8 文件拒绝编辑；保留 BOM。

## 代价
大段改动模型要把整段原文再抄一遍，费 token；没有"一次改多处不同位置"，模型要调用多次。

## 何时要改
eval 里发现"找不到原文"占失败大头时，考虑加模糊匹配（容忍空白差异）。

## 如何验证（eval / 测试）
- tools 的 edit 测试：重复执行幂等失败、CRLF、BOM、`$&`、非 UTF-8。
- **没有用真实模型统计过 edit 失败率**，何时要改取决于这个数据。
