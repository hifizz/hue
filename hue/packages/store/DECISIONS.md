# @hue/store 决定记录

## 1. 要不要存一份派生快照加速大会话启动？

- **选项**：A 只存事件，启动时 `fold(read())`；B 另存消息快照，从快照 + 之后的事件恢复。
- **选了**：A。
- **为什么**：事件是唯一事实源，快照丢了可以重算，事件丢了回不来。实测 10 万条事件顺序读取约 0.17 秒（见 README），一个会话到这个量级之前不需要快照。
- **代价**：会话很大时每次启动都要从头 fold，CPU 和读盘随长度线性增长。
- **何时要改**：fold 10 万条以上的会话启动明显变慢时。快照必须可由 fold 重算并校验（存 `seq` + 内容哈希），校验不过就丢弃重算；不能成为第二个事实源。

## 2. 并发写入同一会话

- **选项**：A 靠主键冲突 + seq 连续性检查拒绝，runtime 保证单写者；B 加会话级锁。
- **选了**：A。
- **为什么**：`BEGIN IMMEDIATE` 一开始就拿写锁，"检查 lastSeq → 插入"之间不会有别的连接插进来；后到的写入因为 seq 对不上被拒绝，而不是悄悄交错。有测试：两个连接写同一会话。
- **代价**：被拒绝的一方得自己处理（重读、重放）。store 不替它决定怎么办。
- **何时要改**：出现真正需要多写者的场景（多个 runtime 进程共享会话）时，需要在 runtime 层做 leader 选举或租约，而不是在这里。

## 3. 会话分叉（fork）——只设计，不实现（LATER）

- **设计**：新会话 = 复制源会话到某个 seq 为止的事件（`seq` 重新从 1 编号，`id` 重新生成），第一个事件是 `session.created`，`parent` 指回源会话。`listSessions` 已经会读 `parent`。
- **为什么先不做**：求职版用不到；而且"复制事件"和"引用源会话前缀"各有取舍（复制简单但占空间，引用省空间但让读取要跨会话），没有真实需求时选不准。

## 4. 实现时做的其他决定

| 决定 | 原因 |
|---|---|
| **一个 `node:sqlite` 实现，零依赖** | Node 22.5+ 内置。更低版本的 Node 在调用 `sqliteStore` 时得到清楚的错误，`memoryStore` 不受影响（`process.getBuiltinModule` 运行时才取）。 |
| **`synchronous = FULL` + WAL** | 进程崩溃（kill -9）时 WAL 加 NORMAL 就够，但"写前日志"要的是 append 返回之后数据一定在，包括断电。 |
| **读取每次取 500 行分页，不用 `iterate()` 游标** | 消费者在 `await` 之间可能很久；分页读不会在这期间占着读游标，边读边写也没问题（有测试）。 |
| **校验逻辑 memory 和 sqlite 共用一份（`check.ts`）** | 两个实现的拒绝规则不会漂移，同一套合同和测试都要过。 |
| **memory 存 JSON 字符串而不是对象** | 读出的是副本；不能序列化的东西在 memory 里也会暴露，不会等换成 sqlite 才发现。 |
| **`listSessions` 不放进 core 的 `EventStore`** | loop 用不到；core 已冻结，加方法要升 `specVersion`。用 `ListableStore` 扩展接口。 |
| **事件原样存（含 `v` 和未知字段）** | 日志要能被将来的版本读懂；store 不解释事件内容。 |
| **读到坏行时报出会话和 seq** | 不让 `JSON.parse` 的异常无头无尾地冒出去。 |

## 5. 一个观察：经过日志后 state 里的 `undefined` 会消失

`runTurn` 内存里的 state 含有值为 `undefined` 的字段（如 `providerMetadata: undefined`、`openTurnId: undefined`）；
从日志 fold 回来的 state 没有这些键。语义相同，但严格的 `deepEqual` 会判不等。对比两者要先过一遍 JSON。
这不是 store 的问题，但**任何拿 `fold(read())` 去和内存 state 做相等断言的人都会踩到**（我在测试里就踩了一次）。
