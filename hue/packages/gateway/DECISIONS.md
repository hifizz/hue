# @hue/gateway 决定记录

> 说明:这个包在开始时**没有设计页也没有任务书**,只有 `docs/packages/deferred.md` 里一行"HTTP / WebSocket / IM 接入,把 Agent 事件流推给客户端"。下面的设计是我自己定的,没有对照过 Pi、Claude Code 或别的 harness 的做法(`TODO(verify)`)。

## 1. 用什么把事件推给客户端:SSE、WebSocket,还是都做?

- **选了**:只做 SSE(事件流)+ 普通 POST(发消息、插话、打断、批准)。
- **为什么**:Hue 的事件流是单向的(agent → 客户端),客户端的动作都是离散的请求,不需要双向长连接。SSE 是普通 HTTP:有 `Last-Event-ID` 续传、穿得过大多数代理、`curl` 就能看、不需要握手升级和帧解析。Node 没有内置的 WebSocket 服务端,手写要自己做握手、掩码、分片、ping/pong——为了得不到额外能力的功能不值得。
- **代价**:浏览器原生的 `EventSource` 不能带 `Authorization` 头,网页端要用 `fetch` 读流(INTEGRATION.md 里有示例)或者在同源反向代理里注入头。SSE 在 HTTP/1.1 下每个浏览器标签页占一个连接。
- **何时要改**:要做双向低延迟的东西(比如语音、实时协作编辑)时。设计页(`deferred.md`)写的"WebSocket"这一项因此没做。

## 2. gateway 怎么拿到 agent?

- **选了**:结构类型 `AgentLike`(`run` / `steer` / `interrupt`),不 import `@hue/runtime`;`agent` 选项既可以是对象,也可以是工厂 `(inputPort) => AgentLike`。
- **为什么**:包之间不互相依赖。runtime 的 `Agent` 满足这个形状。工厂形式是为了解开循环:agent 需要 gateway 的 `InputPort`(批准请求从 HTTP 回来),gateway 又需要 agent。
- **代价**:`AgentLike.run` 的返回值被忽略,拿不到 `RunResult`(用量、`undelivered`)。

## 3. "发消息"一个接口,还是"开始"和"插话"两个?

- **选了**:一个:`POST .../messages`。会话在跑就插话(`steered`),不在跑就开始(`started`)。
- **为什么**:客户端不需要知道会话当前的状态,避免"查询状态再决定调哪个"之间的竞态。gateway 自己同步地记录"谁在跑",所以同时到的两条消息一定是一条 `started` 一条 `steered`(有测试)。
- **边界**:agent 说"在跑"但拒绝插话(刚好在收尾)时返回 `409 session_finishing` + `Retry-After`,而不是悄悄开一个新 turn 或者丢掉消息。
- **代价**:插话的语义(下一个安全点才生效,见 runtime DECISIONS 第 2 条)对客户端是隐含的。

## 4. 事件流:回放和实时怎么衔接才不丢不重?

- **选了**:先订阅(回放期间的实时事件攒进缓冲)、再从 store 读 `after+1` 之后的历史、读完同步地冲掉缓冲并切到实时。durable 事件按 `seq` 去重,只发 `seq` 更大的;delta、progress 这类没有 `seq` 的临时事件只在实时阶段出现。
- **为什么不丢**:runtime 保证"先落盘再 yield",所以到过 hub 的 durable 事件 store 里一定有;"读完"和"切换"之间没有 `await`,没有空隙。**这依赖 agent 用的是同一个 store 并且先写再发**——如果 agent 不这样,会丢事件或者回放读不到。
- **测试**:两种慢回放——读之前卡住(回放和实时都有同一事件,靠去重)、读完快照再卡住(只有实时有,靠缓冲)。
- **代价**:断线重连的窗口里的 delta 丢了(没有 `seq`,无法补);客户端要靠随后到的 `model.message` 拿完整文本。

## 5. 鉴权:谁能做什么?

- **选了**:静态 Bearer token 列表,常量时间比较(对每个 token 都比较,耗时不随命中位置变化);所有 token 权限相同,能访问所有会话。没有 token 必须显式 `insecureNoAuth: true`,且 `listen` 拒绝在非回环地址上这样做。
- **为什么**:最小而不容易配错。OAuth、JWT、按会话的所有权都需要用户系统,这个项目没有。
- **代价**:没有"这个 token 只能看自己的会话"。多租户用法需要在前面放自己的网关,或者每个租户一个 gateway 实例。没有 token 过期和轮换(换 token 要重启)。
- **日志**:错误响应里从不回显 token。

## 6. 防浏览器侧攻击

- **选了**:`Host` 白名单(默认只有 localhost / 127.0.0.1 / [::1])挡 DNS rebinding;带 `Origin` 的请求必须在 `allowedOrigins` 里,否则 403(非浏览器客户端不带 `Origin`)。绑非回环地址时强制设置 `allowedHosts`。`/healthz` 不查 Host(负载均衡器探活用的是 IP)。
- **为什么**:本机的 agent 能执行命令。一个恶意网页如果能让浏览器对 `http://127.0.0.1:8787` 发请求,就是远程代码执行的入口;token 是第二道门,这是第一道。
- **代价**:部署到域名上必须配 `allowedHosts`,配错了会得到莫名其妙的 403(错误信息里会写出被拒绝的主机名)。

## 7. 人工批准怎么走 HTTP?

- **选了**:gateway 实现 core 的 `InputPort`:`request()` 挂起,直到有人 `POST .../inputs/:requestId`、超时(默认 10 分钟)或会话被打断——后两者都按 `cancel` 处理。请求本身由 loop 以 `input.requested` 事件发出,客户端从事件流里看到。
- **安全点**:`requestId` 必须属于路径里的会话,否则 404(不能用 A 会话的路径批准 B 会话的请求);答案格式不对 400,**不会消耗掉**待回答的请求。
- **代价**:谁看到事件流谁就能批准(没有"只有某人能批准")。请求 ID 不是秘密,安全靠 token。

## 8. IM 渠道

- **选了**:一个小接口 `Channel { verify, parse, reply }` 加一个通用实现 `webhookChannel`(HMAC-SHA256,签的是 `时间戳.原始请求体`,时间戳容差 5 分钟)。每个 IM 对话映射成一个会话:`<渠道名>:<对话 ID>`,对话 ID 不规矩时用哈希(不会互相撞)。每个 turn 结束把最终文本回复发回平台。
- **顺序**:先验签、再解析 JSON、再限流。没通过签名的请求不消耗渠道的配额,免得攻击者发垃圾请求把真平台限流。代价:未验签的请求仍然要读完请求体(≤ 1 MiB),**对未鉴权流量的限流要放在反向代理层**。
- **平台看不到内部错误**:agent 抛错时平台上只收到"Sorry, something went wrong on my side.",细节只在 API 的事件流里(`gateway.error`)。
- **局限**:窗口内的重放不会被拦住(没有 nonce);插话进入一个由 HTTP API 启动的会话时没有回复(回复是 turn 的发起方注册的);只回复最终文本,不流式、不发附件。
- **没做**:任何具体平台的适配。每个平台的签名算法、事件格式、"3 秒内必须应答"这类约束都不同,我没有核实过,不写假的。

## 9. 慢客户端和背压

- **没处理**:往一个读得很慢的客户端写事件时,Node 会把数据堆在内存里。有 `maxStreams`(默认 100)限制数量,但没有限制每个连接的积压。
- **为什么没做**:要做就得决定"积压多少算慢、慢了是丢事件还是断开"。断开最简单(客户端凭 `Last-Event-ID` 重连),但我没有办法在测试里可靠地制造一个慢客户端,不想放一段没测过的代码。
- **何时要改**:上线之前。

## 10. 关闭

- **选了**:`close()` 先停止接收新连接、取消所有待批准的请求、用 signal 打断在跑的会话,**等它们收尾(最多 `closeTimeoutMs`)后再关事件流**,订阅者因此能收到最后的 `turn.ended`;不理会 signal 的 agent 不会让关闭一直挂着。
- **代价**:超时后 agent 还在后台跑,日志里可能留下没收尾的 turn;下次对这个会话 `run` 时 runtime 的崩溃恢复会补上。

## 11. 其他

| 决定 | 原因 |
|---|---|
| 会话 ID 由客户端决定,格式 `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}` | 没有"创建会话"的往返;格式限制挡住路径穿越和奇怪字符。客户端用 UUID 就行。 |
| 错误统一为 `{ "error": { "code", "message" } }`,`code` 是稳定的字符串 | 客户端按 `code` 分支,不解析 `message`。 |
| 内部错误只回通用的 500,细节给 `onError` | 不把堆栈、连接串之类泄露给客户端(有测试)。 |
| 限流是进程内的固定窗口 | 简单够用;窗口边界处最多放过 2 倍;多实例各算各的。 |
| 请求体上限 1 MiB,文本上限 10 万字符 | 声明了 `Content-Length` 的超限请求干净地回 413;分块传输读超了只能断开连接。 |
| 同时在跑的会话上限(默认 8) | 每个会话都在花模型的钱、占沙箱。超出回 429 + `Retry-After`。 |
| `Content-Type` 必须是 `application/json` | 挡住用表单提交跨站请求(CSRF)的简单做法。 |
| 不做会话列表接口 | store 的 `listSessions` 不在 core 的 `EventStore` 端口里。 |
