# @hue/context 决定记录

## 0. 切在哪里：长任务里的切点

- **问题**：编码 agent 的一个任务通常只有**一条**用户消息，后面是几十步工具调用。如果只允许切在 user 消息之前，`truncate` / `summarize` 在这种长任务里无处可切，起作用的只有 `foldToolResults`。（最初的版本就是这样，写在这里是为了留个对照。）
- **选了**：可以切的位置有两种：某条 user 消息之前，或**紧跟 tool 消息之后的 assistant 消息之前**。被丢掉的最后一条是完整的 tool 消息，保留下来的 assistant 的结果就跟在它后面，所以 tool-call 和 tool-result 仍然不会被拆开；保留的第一条是 user 或 assistant（前面接替换进去的 user 消息），provider 都接受（`@hue/ai` 会合并连续的 user）。有一个对所有预算和参数组合都检查结构的测试。
- **任务原文要带过去**：切在一轮中间时，这一轮的任务（最近一条用户消息，可能是 steer 插话）会落进被丢掉的部分。替换消息 = 任务原文 + 说明 / 摘要，否则 agent 会忘了自己在做什么。再压一次时，上次留下的说明 / 摘要会被认出来、不再当成"任务"抄一遍，所以任务只出现一次、说明不叠加。带过去的任务也计入预算。
- **保护最近的部分**：`keepTurns` 仍然是最近几轮不动，但这些轮里**最早的一轮允许从中间切**，只要切完至少还剩 `keepSteps` 步（默认 6，一步 = 一条 assistant 和它的工具结果）。所以多轮对话里短的最近几轮仍完整保留，一条消息的长任务也能压。
- **代价 / 局限**：
  - 保留的最近几步可以比预算还大——`keepSteps` 是下限，不是上限。单个工具结果很大时（比如 6 步各读一个大文件），光靠 `truncate` 压不进去，要靠 `foldToolResults` 先把结果折掉，所以长任务的推荐组合仍是 `chain(foldToolResults(), summarize())`。
  - 旧的几轮现在也可能从中间被切（保留 `done 3` 却没有问它的那条用户消息）。信息上没有损失（任务原文带过去了），但历史会显得不连贯。
  - 被丢掉的步骤里的 assistant 文字（它当时的推理）只有 `summarize` 会留下大意。
- **何时要改**：真实长任务跑出数据之后，看 6 步是不是合适的下限，以及摘要后 agent 有没有重复做已做过的事。

## 1. 何时触发压缩？

- **选了**：每一步调模型前，估算（系统提示 + 工具说明 + 消息）超过预算就压。预算默认是模型上下文窗口的 **80%**，可以显式指定。另外 loop 收到 `context_overflow` 后会带 `overflowed: true` 重来，这时无条件压。
- **压到哪**：预算的 **50%**，不是刚好压到线下。每次压缩都会改写前缀、让 prompt cache 失效（`@hue/ai` 在最后一条消息上放了缓存断点）；压到刚好卡线，下一步又超，等于每步都付一次缓存的代价。压到一半，要再涨回线上才会再压。
- **超窗重试**：我们的估算这时已经被证明低估了，所以不信它——目标取 `min(目标, 当前估算 × 0.6)`，至少压掉 40%。
- **代价**：80% / 50% 都是经验值，没有用真实任务调过。
- **何时要改**：有了真实长任务的 `HUE_TRACE` 数据，对比缓存命中率和压缩频率之后。

## 2. 压缩结果写回日志还是只在内存？

- **选了**：写回，用 core 已有的 `context.compacted` 事件（core 在设计时就定了）。`Compaction.replacement` 存的是替换进去的完整消息，所以**回放不需要再调一次模型**，摘要也不会因为重放而变。
- 有集成测试：压缩事件落进日志后，`fold(日志)` 和 turn 结束时的 state 相等；transcript 从不删。
- **代价**：摘要全文进了日志，日志会变大；多次压缩每次都存一份完整的 replacement。

## 3. token 计数：近似还是 tokenizer？

- **选了**：近似，且**故意偏高**：ASCII 每字符 0.3 个 token，非 ASCII 每字符 1 个，每条消息加固定开销，图片 / 文件按 1500 算，推理块的签名也算。
- **为什么**：零依赖；估高只会让压缩早一点，估低要等 API 报错才发现（那时已经浪费一次请求）。
- **没用 `ModelPort.countTokens`**：`@hue/ai` 还没实现它，中转站也不一定转发计数端点。
- **代价**：中文偏高不多，英文代码按约 3.5 字符一个 token 算，偏高约 5%，会比必要的略早压。（这个 3.5 也是经验值，没量过。）
- **何时要改**：接了 Anthropic 的计数端点，或者拿到估算和 `usage.inputTokens` 的真实对比数据之后。

## 4. 三种策略

| | 做什么 | 优点 | 缺点 |
|---|---|---|---|
| `foldToolResults` | 把旧的大工具结果换成一句占位说明（保留调用、工具名、`isError`），最近 `keepRecent` 条原样，折到放得下为止 | 不调模型、可恢复（重跑工具）、**长任务内部也能用**、编码 agent 里体积大头就是工具结果 | 不折叠 assistant 自己写的长参数（`write` 的整文件内容） |
| `truncate` | 丢掉最早的若干轮 / 若干步，换成一句"你忘了这些"的说明（任务原文保留） | 最便宜、可预测 | 信息完全丢 |
| `summarize` | 让模型把被丢的部分写成摘要，最近 `keepTurns` 轮保留原文 | 保留信息最多 | 多一次模型调用；摘要可能漏关键细节 |

- `chain(a, b)`：依次试，前一个压完还超，后一个接着压。典型用法 `chain(foldToolResults(), summarize({ model }))`：先用不花钱、可恢复的折叠，不够再付摘要的代价。后一个策略不会因为"超窗重试"再无条件压一次。
- **摘要怎么防丢信息**：prompt 要求保留确切的路径、命令、报错、数字，并合并上一次摘要而不是重复；最近两轮留原文；摘要请求里的 tool-call 被渲染成纯文本（摘要模型没有工具定义，带 `tool_use` 块的请求会被 provider 拒绝）；每个工具结果截到 1500 字符。
- **摘要失败怎么办**：模型报错、输出为空、抛异常、没有 finish → 退回 `truncate` 的做法，日志里 `strategy` 写成 `summarize→truncate`。宁可丢信息，也不能让 agent 因为压缩失败而卡死。被取消时不压缩，让 loop 自己处理取消。
- **要摘要的内容比摘要模型的窗口还大**：保留靠后的部分（离现在近的更重要），前面标明被省略。
- **没有数据证明摘要质量**：验收里的"三种策略在 eval 上有对比数据"要等 `@hue/eval`。现在只验证了机制（下标换算、配对、失败回退），没验证"摘要有没有丢掉关键信息"。

## 5. 在已压缩的视图上再压：下标换算

策略工作在"已应用上一次压缩的视图"上，而 core 的 `Compaction` 是"把**完整 transcript** 的前 `throughIndex` 条换成 replacement"。`engine.ts` 的 `toCompaction` 负责换算：切点落在旧 replacement 之后，`throughIndex` 往后推；落在旧 replacement 里面，`throughIndex` 不动，旧 replacement 没被切到的尾巴接在新 replacement 后面。有测试证明 core 的 `modelView` 套这个 `Compaction` 得到的和策略返回的消息完全一致。

## 6. 其他

| 决定 | 原因 |
|---|---|
| 策略共用一个外壳（`engine.ts`），具体策略只回答"给定视图和空间，怎么改" | 触发、目标、下标换算、"没变化就不写 Compaction"只写一份。 |
| 切点越界直接抛错 | 悄悄生成坏数据会在几步之后才以 provider 400 的形式冒出来。 |
| 替换结果和原来一模一样就不返回 `compaction` | 避免往日志里写无意义的事件。 |
| 压缩不动 `instructions` 和工具列表 | 它们每步固定，是缓存前缀的一部分；core 的 `ContextStrategy` 也只管消息。 |
