# @hue/eval 决定记录

## 1. 评分：测试通过，还是 LLM judge？

- **选了**：只做客观的——一条命令，退出码 0 算通过。没有 LLM judge。
- **为什么**：judge 本身要被评测，多一层不确定性；编码任务有测试就够。最小版先保证"通过"这个数字可信。
- **代价**：判不了没有测试可写的任务（总结、解释、开放式调研）。
- **何时要改**：加那类任务时。到时 `check` 里可以调模型，接口不用动。

## 2. 防作弊：agent 能不能改测试？

- **选了**：判分前把 `tests` 里的文件原样写回，再跑判分命令。agent 看得到测试（要靠它复现问题），但改了没用。有测试证明（把 `test.js` 改成什么都不测，仍然不通过）。
- **代价**：只保护列在 `tests` 里的文件。agent 若改了测试依赖的别的文件（比如把被测函数换成硬编码答案）拦不住——硬编码在这个规模的题里靠"测试多几个用例"挡，不靠机制。判分命令本身是任务作者写的，默认可信。
- **何时要改**：任务多了、有隐藏测试的需求时（agent 看不到的用例）。

## 3. 判分在哪里跑？

- **选了**：在 agent 用的同一个执行环境里（`check` 拿到 `sandbox`）。runner 负责创建和 `dispose`，所以 eval 不依赖具体是 local 还是 Docker。
- **为什么**：agent 写的代码不能在宿主上跑——用 Docker 隔离就是为了这个，判分时再放回宿主等于白隔离。
- **代价**：判分命令要能在那个环境里跑（镜像里得有 node）。

## 4. 耗时、超时和 `error`

- **选了**：耗时只算 agent 跑的时间（不含 setup、check）。超时打断 agent，状态 `timeout`，**不再跑 check**（超时就是没完成，哪怕文件碰巧对了）。runner 抛错、setup 失败、check 抛错都是 `error`，不是 `fail`。
- **为什么**：`error` 是评测的问题（Docker 没起来、磁盘满），算进 agent 的失败会把成功率压低又查不出原因。报告里单独计数并警告。
- **代价**：`error` 仍然算在成功率的分母里，没有悄悄排除——排除了会让数字好看但不诚实。

## 5. 失败在哪一层

- **选了**：`layerOf` 看最后一个 `turn.ended` 的原因和工具失败比例，给一个粗标签。
- **诚实的局限**：`wrong-result` 只是"agent 正常结束了但结果不对"，原因（没读懂、改错地方、没跑测试）看不出来；`tools` 的"一半以上调用失败"是拍脑袋的阈值。设计页要的"失败案例分析模板"（现象、哪一层、改了什么、前后数据）是人写的，这里只给了素材：最后几步和会话 id。
- **何时要改**：跑出真实失败之后，看哪些标签真的有用。

## 6. eval 和 agent 的关系

- **选了**：eval 只认 `AgentRunner = (job) => Promise<void>`，agent 把事件交给 `job.onEvent`。eval 不 import runtime，组装在 `examples/eval.ts`。
- **为什么**：包之间不互相 import；也意味着任何能产出 `HueEvent` 的东西都能被评。
- **没做**：对照组。同模型下 Pi / Claude Code 没有 `HueEvent`，要先写适配器把它们的输出转成事件（或者只比较"测试是否通过"和耗时，不比 token 和步数）。设计页的 `DECIDE: 对照组` 仍然开着。

## 7. 其他

| 决定 | 原因 |
|---|---|
| 任务 5 个，不是设计页的 20 个 | 最小版先验证流水线；题目质量比数量重要。每道题自检过，但没跑过真实模型，不知道难度。 |
| 每次试跑都是新的临时目录；没通过的默认保留 | 保留现场才能去看；通过的删掉，不然 /tmp 会堆满。 |
| `trials` 默认 1 | 模型有随机性，想看稳定性要自己设大；报告里"成功"是 passes/trials，不做 pass@k。 |
| 不做任务集的 CLI 和配置文件 | 任务是代码（TypeScript 对象），不是 YAML；`examples/eval.ts` 够用。 |
| 报告同时输出 Markdown 和 JSON | 前者给人看，后者给以后做前后对比用；JSON 里不含事件，只有指标。对比脚本还没写。 |
