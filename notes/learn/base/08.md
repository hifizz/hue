先对照真实的 provider 代码确认一下，这样我说的是实际行为，不是凭印象。

你的理解基本对：**模型本身给的是结构化的**，`message.content` 里的 `tool-call` 是在 `model.complete()` 这一层（也就是 provider 适配器）处理好的，不是 loop 解析的。但中间有一层需要说清楚。

## 先分清两件事

模型厂商的 API 有两种返回方式：

**非流式**：响应体本身就是结构化 JSON。以 Anthropic 为例，`content` 数组里直接有一个 `{type: "tool_use", id, name, input: {...}}` 块，`input` 已经是对象。你只需要把它改个字段名，不用解析。

**流式**：这是需要"处理"的地方。模型是一个 token 一个 token 往外吐的，工具参数也是这样到达的，是**碎片化的 JSON 字符串**：

```
{"type":"tool_use","id":"toolu_01","name":"calc"}     ← 先到，只有名字，没有参数
{"partial_json":"{\"a\": 1"}                          ← 碎片 1
{"partial_json":"2, \"op\":"}                         ← 碎片 2
{"partial_json":" \"*\", \"b\": 3}"}                  ← 碎片 3
content_block_stop                                     ← 这个块结束了
```

任何一个碎片单独拿出来都不是合法 JSON，必须全部到齐、拼成完整字符串、再 `JSON.parse` 才能得到 `{a:12, op:"*", b:3}`。

## 我在源码里确认到的

我读了你项目里 `@ai-sdk/anthropic` 的流式代码：

- 收到 `tool_use` 开始块时，建一个缓冲区，记下 `toolCallId` 和 `toolName`（`index.js:4918`）
- 每个 `input_json_delta` 到达时，把 `partial_json` 追加到缓冲区，同时往外发 `tool-input-delta` 事件给 UI 显示"正在生成参数"（`index.js:5420`）
- `content_block_stop` 到达时才发出完整的 `tool-call`（`index.js:5307` 附近的 `case "content_block_stop"`）

OpenAI 兼容协议是同样的思路：`pending.bufferedArguments += argumentsDelta`（`openai-compatible/dist/index.js:738`），而且它的 `arguments` 在协议里**本来就是字符串**（`z3.string()`），需要 `JSON.parse`。

## 所以回答你的三个问题

**1. 是谁处理好的？** 是 provider 适配器，也就是 `@ai-sdk/anthropic`、`@ai-sdk/openai-compatible` 这些包，它们实现了 `LanguageModel` 接口。AI SDK 的核心（`streamText`）收到的已经是拼装完整的 `tool-call` 事件。

**2. 你说的"model.complete 的 SDK 会自动处理"对吗？** 对，在本课里 `Model.complete()` 就扮演这个角色。我的假模型直接返回做好的 `ToolCallPart`，所以 loop 不用管拼装。这是我为了先讲清楚循环做的简化，真实世界里这一层是一个单独的、有难度的工作。

**3. loop 里完全不需要解析了吗？** 还是有一点：拼装完整不等于**内容正确**。

## 还剩两件事 loop 必须自己处理

读 `parse-tool-call.ts` 能看到 AI SDK 在 loop 这一层还做了两个检查，对应两种失败：

| 失败 | 原因 | AI SDK 怎么做 | Hue 怎么做 |
|---|---|---|---|
| `NoSuchToolError` | 模型编了一个不存在的工具名 | 先给 `repairToolCall` 一次机会，否则标记 `invalid: true` | `loop.ts:208` 返回 `Unknown tool` 的错误结果 |
| `InvalidToolInputError` | JSON 拼完整了但不符合 schema，或者 JSON 本身是坏的（模型偶尔会输出不合法的 JSON） | 同上 | `tool.parse` 校验失败，或者 `{__raw: string}` 保留原文，转成错误结果 |

这就是 Hue 的 `ToolCallPart.input` 注释写"解析失败时保留原文 `{ __raw: string }`，交给 loop 报错给模型"的原因：适配器尽力拼装，拼出来不是合法 JSON 就不要丢，原样带上去，由 loop 统一报错给模型重试。

## 对照 Hue 的分工

```
provider 的原始字节流
    │  @hue/ai（ModelPort 实现）：拼碎片、JSON.parse、统一成 Hue 的 ModelChunk
    ▼
ModelChunk: {type:'tool-call', callId, name, input}   ← 参数完整才发一次
    │  core 的 loop：收集进 assistant.content
    ▼
message.content 里的 ToolCallPart
    │  loop：校验工具名、校验参数 (tool.parse)
    ▼
执行
```

`docs/tasks/wave-1/01-ai.md` 把"流式 tool-call 拼装"标成最难的、必须人审的部分，就是因为这一层看似简单，实际要处理的情况很多：参数为空对象时 provider 不发任何 delta、同一个响应里多个 tool-call 的碎片交错到达、不同 provider 的 id 和 name 到达时机不同。
