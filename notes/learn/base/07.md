# 面试讲 RAG：该讲什么

先给一句话版本，面试开口就能用：

> RAG 是在调用模型之前，先从外部知识库里检索出相关片段，放进 prompt。它解决的是模型"不知道私有或最新信息"的问题，同时避免把整个知识库塞进上下文。

## 一、为什么需要 RAG（开场先讲这个）

要讲清楚它解决的三个问题，每个都和你前面学的内容相连：

1. **模型无状态且知识有截止日期。** 它不知道你公司的文档，也不知道昨天的新闻。
2. **上下文窗口有限，而且越长质量越差。** Anthropic 的 compaction 文档里明确写了：*"response quality degrades as a conversation grows"*。所以不能把所有资料都塞进去。
3. **成本。** 前面讲过每个 step 都要重发整个 messages，塞得越多越贵。

RAG 的思路是：**只在需要的时候，取最相关的一小块。**

## 二、完整流程（能说清这个，就算搞懂了）

分离线和在线两个阶段：

**离线（建索引，只做一次，文档更新时重做）**

1. **切块（chunking）**：把文档切成几百 token 的片段。不能整篇文档做一个向量，因为一个向量表示不了太多内容。
2. **向量化（embedding）**：用 embedding 模型把每个片段变成一个向量（一串数字），语义相近的文本向量也相近。
3. **入库**：向量连同原文存进向量数据库。

**在线（每次提问）**

4. **查询向量化**：用同一个 embedding 模型把用户问题也变成向量。
5. **相似度检索**：在库里找最接近的 top-K 个片段（通常用余弦相似度）。
6. **拼进 prompt**：把这些片段连同问题一起交给模型，让它基于片段回答。

一句话记忆：**切块 → 向量化 → 入库 → 查询向量化 → 找最近的 → 塞进 prompt。**

## 三、面试官最爱追问的难点（这才是拉开差距的地方）

### 1. 切块会丢上下文

这是 Anthropic 在 Contextual Retrieval 文章里举的例子：一个片段写着"公司营收比上季度增长了 3%"，但没写是哪家公司、哪个季度。单独拿出来，向量就检索不准。

**解决办法（Contextual Retrieval）：** 在切块之后、向量化之前，用一个小模型给每个片段前面加一段 50 到 100 token 的说明（"这是 ACME 公司 2023 年 Q2 财报中的一段……"）。成本靠 prompt caching 压低，Anthropic 给的例子是每百万文档 token 约 1.02 美元。

### 2. 光靠向量不够，要混合检索

向量擅长语义相近，但不擅长精确匹配（比如错误码、人名、函数名）。所以常见做法是同时建 **BM25**（关键词匹配）索引，两路结果用**排名融合（rank fusion）**合并。

### 3. 先多取，再重排（rerank）

先召回一大批候选（Anthropic 实验里取 150 个），再用一个专门的重排模型对每个打相关性分，只留前 20 个给主模型。代价是多一点延迟和成本。

### 4. 有数据可以引用

Anthropic 报告的检索失败率（以 top-20 召回失败率计，基线 5.7%）：

| 方案 | 失败率 | 降幅 |
|---|---|---|
| 基线（普通向量检索） | 5.7% | |
| + Contextual Embeddings | 3.7% | 35% |
| + Contextual BM25 | 2.9% | 49% |
| + 重排 | 1.9% | 67% |

面试时讲"每一层改进带来多少收益"，比泛泛说"我优化了检索"有说服力得多。

### 5. 怎么评估 RAG 好不好

分两层：检索质量（召回率、相关性）和最终回答质量。要先建一小批"问题 → 应该找到的片段"的标注集，改任何一环都跑一遍对比。这也对应你项目里 `@hue/eval` 的思路。

## 四、更高级的加分点：什么时候不该用 RAG

这个对你特别有用，因为你在做 harness，面试官很可能想听你对 agent 的看法。

Claude Code 的创建者 Boris Cherny 在访谈里说过：早期版本确实用了本地向量库做 RAG，但团队很快发现他所说的"agentic search"（本质就是 glob 加 grep，让模型在循环里自己搜）效果更好。据报道的理由有四点：

- **新鲜度**：索引会和代码脱节，刚写的函数还没被索引
- **权限和隐私**：算 embedding 要把代码发到云端
- **精度**：grep 是精确匹配，向量会有模糊的误命中
- **简单**：不用建和维护索引

这件事的价值在于它体现了一个思路：**RAG 是"一次性检索，再回答"；agentic search 是"模型在 loop 里自己决定搜什么、搜几次"。** 后者正好就是你刚写的 agent loop 加上一个搜索工具。

注意：这一段来自二手来源转述（我没拿到访谈原文），面试里建议说"据 Boris Cherny 公开访谈提到"，不要说得比这更绝对。另外有来源指出，向量检索对自然语言文档仍然适合，代码检索和文档检索是两种场景。

## 五、和"上下文压缩"的关系（你项目里的两个包）

这两个经常被混淆，一句话区分：

- **上下文压缩（`@hue/context`）**：处理**对话本身变长**。把旧的 messages 总结成摘要，或清掉旧的工具结果。Anthropic 的 compaction 就是服务端帮你把旧轮次替换成摘要。
- **RAG / 记忆（`@hue/memory`）**：处理**外部知识太多**。在需要时才取回相关内容。

你的 `docs/04-challenges.md` 里已经有一条很好的答案：压缩的质量看不见，摘要丢了关键信息不会报错，只会让 agent 20 轮后变笨，所以要用 eval 里"必须记住早期细节"的长任务去测。

## 六、建议的 3 分钟讲法

1. 问题：模型不知道私有知识，上下文又有限（20 秒）
2. 流程：离线切块、向量化、入库；在线查询向量化、检索、拼 prompt（40 秒）
3. 难点：切块丢上下文，用 Contextual Retrieval；向量不精确，加 BM25；再加重排。给出 5.7% 降到 1.9% 的数据（60 秒）
4. 评估：建标注集，分检索和生成两层看（20 秒）
5. 反思：agent 场景下 Claude Code 为什么改用 grep，RAG 和 agentic search 各自适合什么（40 秒）

# 评测怎么提升回答质量，以及怎么给面试官讲你的迭代

先回答你的困惑，因为这是整个话题的根。

## 一、评测为什么能提升质量：它本身不提升

**评测不会让回答变好。它只做一件事：把"感觉变好了"变成"可以比较的数字"。** 真正让回答变好的是你改的东西：prompt、模型、工具描述、检索策略、压缩方式。评测的价值在三个地方：

1. **能判断改动是真进步还是错觉。** 不评测时，你改了 prompt，试了两三个问题觉得不错，就上线了。可能这三个变好了，另外十个悄悄变差了。
2. **能防止回退（回归）。** 今天修好的问题，下周改别的东西时又坏了。有固定题集，每次改动都跑一遍，坏了立刻知道。
3. **能定位问题出在哪一环。** 回答差可能是检索没找到、工具参数错、模型没按指令、摘要丢了信息。分项打分能让你知道该改哪里。

所以完整的话是：**评测提供反馈信号，迭代靠改动加反馈信号的循环。**

### 这个循环长什么样

```
发现问题 → 把它固化成一道题 → 先确认旧版本确实答不好
        → 做一个改动 → 在同一批题上重跑
        → 对比分数变化 → 没变坏才发布 → 线上出现新问题 → 回到第一步
```

关键在"固化成一道题"：每个线上发现的问题，变成题集里永久存在的一题，以后任何改动都不能让它再坏。题集随着时间越攒越有价值。

## 二、你项目里真实存在的东西（可以放心讲）

我读了 `evals/agent/` 和 `docs/observability/07-loop-engineering.md`，你的设计其实已经是上面那个循环：

**1. 题（case）有固定结构。** 每题有稳定 ID、输入、预期（路由、调用哪些工具、终态、必须包含或不得包含的内容、JSON 字段）。例如 `core-english-instruction-following`：要求"一句话解释幂等、不要列表"，断言回答包含"repeat"、不包含"1."。

**2. 评分分两类，并且刻意分开。**
- **确定性评分**（deterministic）：包含、排除、工具调用对不对、有没有泄露。能做硬性失败判定。
- **模型裁判**（judge）：对 correctness、faithfulness、helpfulness、completeness、citationSupport 五个维度各打 0 到 1 分。

你的文档里有一条设计原则很值得讲：**裁判分数不能覆盖确定性硬失败**（`judge.ts` 的 system prompt 里也写了 "do not override deterministic safety failures"），并且**不把多个维度压成单一总分**。

**3. 对比有严格的前提检查。** `compare.ts` 会拒绝比较不可比的东西：snapshot 版本不同、模式不同、题集版本（dataset revision）不同、case 集合对不上，都直接报错，而不是悄悄取交集。比较报告列出配置指纹差异、硬失败变化、裁判分变化、延迟 p50 和 p95、用量、provider 重试和回退次数。

**4. 门禁规则明确。** PR 只被"稳定的确定性硬失败"阻断；误报必须由代码所有者书面 override，并新建修正 case，不能直接删掉失败的题。

**5. 版本可追溯。** 每次运行记录配置指纹、题集 revision、评分器版本，裁判模型加 rubric 版本会写进 evaluator version。这样两次结果为什么不同，能查到是哪个变量变了。

**6. 三档频率。** PR 上跑 fixture（快、不花钱）；每周定时跑全部 fixture；发布前跑 release 档，保留 Experiment URL 和比较报告。

**7. 线上信号回流的设计（07 文档第 1 节）。** 在 Langfuse 里按 release、错误类别、延迟、`product-feedback=down` 找候选 trace，脱敏后做成新 case。文档强调：**先让新 case 在旧版本上稳定复现问题**，避免只为当前修复写"必过"的答案。

## 四、面试怎么讲：三种诚实程度的讲法

### 如果你有真实跑过的结果（最强）

> 我发现文档工具有个问题：混用来源时模型会拿网页 ID 去读项目文档。我先做了 6 道题复现这个问题，用旧版本跑出 X% 通过率。改了工具协议后，同样 6 题跑新版本，通过率变成 Y%，重复调用失败的次数从 A 降到 B。我用 3 次重复排除随机波动。

（X、Y、A、B 必须是你真实的数字。）

### 如果只有体系，没有结果（诚实的讲法）

> 我把评测当成改动的反馈系统来搭，而不是事后打分。核心有三个设计：确定性检查和裁判分数分开，裁判不能覆盖硬失败；比较器拒绝比较不同题集版本的结果；线上差评会被做成新 case 并先在旧版本上复现。目前这个闭环我完成了 fixture 和 CI 层，真实线上数据回流这一步还没跑通，我的下一步是用一个已知问题完整走一遍。

这个讲法的好处是：**面试官会认为你知道正确的做法，也知道自己的边界。** 比夸大更安全，也往往更受认可。

### 被追问"评测怎么提升了回答质量"时的回答骨架

1. **先说清评测不直接提升质量，它提供反馈。**
2. **举一个具体循环：** 发现问题 → 固化为题 → 旧版本复现 → 改动 → 重跑对比 → 门禁。
3. **说出三个陷阱（这是拉开差距的地方）：**
   - **裁判模型有偏差**：所以你配了人工标签校准小集（`fixtures/judge-calibration.json`），调 rubric 时复核 MAE（平均绝对误差）
   - **随机波动**：模型每次输出不同，所以要重复多次，不能把单次差异当结论
   - **题集过拟合**：为了让某道题通过而改 prompt，可能让其他情况变差，所以要看全量题集而不是只看那一题。你的文档里"避免只为当前修复写必过答案"就是在防这个

## 五、最容易被问倒的几个问题和答案

| 问题 | 建议回答 |
|---|---|
| 怎么知道裁判模型打的分靠谱？ | 不能直接信。用一小批人工打过标签的样本校准，看裁判分和人工分的平均误差，调整 rubric 后重新校准。裁判只用于质量维度，不用于安全硬判定。 |
| 同一个题每次结果不一样怎么办？ | 重复多次（你的实验设计是 3 次），看分布而不是单次；确定性断言写成"必须包含的事实"，而不是精确字符串。 |
| 评测题从哪来？ | 两个来源：设计时覆盖已知风险（路由、工具、安全、记忆泄露）；线上差评和错误回流，脱敏后做成新题。 |
| 怎么防止评测数据泄露隐私？ | 默认只用合成或公开 fixture；真实片段必须去身份化并标 `authorized-private`，默认不上传 Langfuse Dataset。 |
| 线上用户的👎怎么用？ | 它只是一个独立信号，不是质量标签（你的文档原话）。用它筛出候选 trace，人工复盘后才做成题。 |
| 评测分数高了线上就一定好吗？ | 不一定。题集是合成的，不代表真实流量分布。你的压缩评测文档里也写了："不得将八个关联检查点解释成独立样本的线上故障率"。 |

最后一行是个很好的例子，说明你知道**评测结论的适用范围**，面试官通常会对这种克制印象很深。

## 六、一个小提醒：把"可观测"和"评测"的关系讲清楚

两者容易被混为一谈，一句话区分：

- **Langfuse 观测**回答"线上发生了什么"（trace、延迟、成本、👎）
- **评测**回答"这次改动是不是更好"（固定题集、旧新对比）

线上观测发现问题，评测验证修复，修复上线后再观测。这就是你文档里那张环形图的意思。
