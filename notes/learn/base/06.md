# 提示缓存：哪些参数动了会失效

先给结论：缓存按**前缀**匹配，前缀的顺序是 `tools → system → messages`，前面的任何一个字节变了，后面全部失效。所以保缓存的原则只有一条：**请求从头到尾是上一次请求的严格延长，只在末尾追加。**

下面的内容来自 Anthropic 的 prompt caching 文档和 OpenAI 的 prompt caching 文档（两份文档都很长，我读到的是前 10 万字符，Anthropic 文档后半部分没读）。

## 一、缓存是怎么工作的

**Anthropic：**
- 文档原话：缓存引用整个 prompt，`tools`、`system`、`messages` 依次排列，直到被 `cache_control` 标记的那个块。
- 变化的影响是级联的：*"Changes at each level invalidate that level and all subsequent levels."*
- 默认 5 分钟寿命，每次命中**免费续期**。写入价 1.25 倍，读取价约 0.1 倍（Opus 5.5 和 Sonnet 5.5 是 0.05 倍，Fable 5.1 是 0.025 倍）。1 小时寿命的写入价是 2 倍。
- 最多 4 个断点。每个断点向前最多回看 20 个块找命中。
- 最小可缓存长度因模型而异：Claude 5 系列大多是 512，Opus 4.5/4.6 和 Haiku 4.5 是 4096。不够长**不会报错，只是不缓存**。

**OpenAI：**
- 自动缓存，不用标记，按前缀匹配。GPT-5.6 起最小 1024 token，也支持显式断点。
- 价格：读取约 0.1 倍。GPT-5.6 起写入要加价（30 分钟寿命 1.25 倍）。
- `prompt_cache_key` 影响请求路由，把相关请求导到同一台机器。文档建议每个 key 每分钟约 15 个请求，超过会溢出到别的机器，命中率下降。

## 二、各参数改动后的影响

下表来自 Anthropic 文档的失效表（✘ 表示失效，✓ 表示不受影响）：

| 改动 | tools 缓存 | system 缓存 | messages 缓存 |
|---|---|---|---|
| 工具定义（名字、描述、参数） | ✘ | ✘ | ✘ |
| `tool_choice` | ✓ | ✘ | ✓ |
| 增删图片（任何位置） | ✘ | ✘ | ✓ |
| thinking 参数 | 因模型而异 | 因模型而异 | ✘ |
| effort | 因模型而异 | 因模型而异 | ✘ |

注意表格列的含义：每格表示"这类改动之后，该层缓存是否**保持有效**"。我对表格的原始呈现不是 100% 确定（抓取工具返回的是摘要），但文档同时有一句明确的话：*"Tool definitions are the most disruptive change: modifying names, descriptions, or parameters invalidates everything."* 这一条可以放心当结论。

映射到 AI SDK 的参数：

| streamText 参数 | 对缓存的影响 | 建议 |
|---|---|---|
| `tools`（定义本身） | 最严重，全部失效 | 一个 session 内不增不减不改描述 |
| `toolOrder` / 工具对象的 key 顺序 | OpenAI 明确说工具"顺序"算前缀的一部分 | 显式设置 `toolOrder` 固定顺序 |
| `activeTools` | 会改变实际发给 provider 的 `tools` 数组 | **见下文，这是最大的坑** |
| `toolChoice` | Anthropic：system 缓存失效；OpenAI：建议用 `none` 而不是删工具 | 尽量少变，变了也只影响 system 以后 |
| `instructions` / `system` | 改动使 system 及之后全部失效 | 动态内容不要放在这里 |
| `messages` | 只追加不改写则前缀保持 | 压缩、截断、重写历史都会重置缓存 |
| `reasoning` / `providerOptions.anthropic.effort` / `thinking` | thinking 配置变化总是使 messages 缓存失效 | 一个 session 内别变 |
| `maxOutputTokens` | 文档没有列为失效因素 | 但在旧模型的 budget 模式下，thinking 预算由它按百分比算出，会间接改变 thinking 参数 |
| `model` | 不同模型缓存互相独立 | `prepareStep` 里换模型等于从头冷启动 |
| `temperature` 等采样参数 | 不在失效表里 | 不用担心 |

## 三、对你项目最重要的几个坑

### 坑 1：`activeTools` 会让工具数组变化，缓存失效

我读了 `stream-text.ts`：`filterActiveTools` 过滤后的结果直接进入 `prepareTools`，**真的会少发工具给 provider**，而不只是"在本地忽略"。

你的 `createToolStepPolicy` 在最后一步（`stepNumber >= 19`）把 `activeTools` 过滤成空，意思是那一步 `tools` 数组变成空。按 Anthropic 的规则，这会让那一步及以后的缓存全部失效，而且还不止一次：第 19 步的请求前缀是"没有工具"的版本，与前 19 步完全不同。

不过这个影响有多大要看情况：这是研究模式的最后一步，且只发生一次，付出的是"最后一步整个上下文按全价输入"。研究模式上下文往往很长（搜索结果多），这一步可能不便宜。

OpenAI 文档对这类需求的建议是：**用 `tool_choice: "none"` 而不是删掉工具。** 你也可以这样做：最后一步保留 `activeTools`，改成 `toolChoice: "none"`。我没有验证 AI SDK 的 `toolChoice: "none"` 对 Anthropic 是否也保留 tools 数组，但从 `ToolChoice` 类型看 `'none'` 是合法值。

另外 Anthropic 的表里 `tool_choice` 改动会使 **system 缓存失效**（messages 保持）。也就是说"最后一步用 `toolChoice: 'none'`"并不是完全免费，只是比删工具轻。这两个方案谁更划算，需要拿你自己的数据测。

### 坑 2：第 0 步的强制 `toolChoice`

`stepNumber === 0 && forceWebFirst` 时设了 `toolChoice: { type: "tool", toolName }`，第 1 步又回到 `"auto"`。按上表，`tool_choice` 变化会使 system 缓存失效，也就是第 0 步和第 1 步的前缀在 system 之后就不同了。

不过第 0 步通常是这次对话的第一个请求，本来就写缓存，所以问题主要是：**第 1 步没法读第 0 步写入的 system 缓存**。如果 system 很长，这是一笔浪费。

### 坑 3：thread-chat 的缓存标记在 legacy-chat 这条路径上根本没用

我 grep 了：`decoratePromptCache`（给 system 和历史消息打 `cacheControl` 的函数）只在 `lib/thread-chat/streaming/generation-plan.ts` 里被调用，**`app/api/chat/route.ts` 里没有任何缓存相关代码**。

所以 route.ts 这条 legacy-chat 路径对 Anthropic 来说，我没有看到任何显式的 `cache_control` 标记。是否有缓存命中，取决于：
- `@ai-sdk/anthropic` 或网关有没有自动加标记（我没查）
- 你用的是 `token-router` 这个中转，它是否对缓存做了处理（我没查）

建议先看 `usage` 里的 `cache_read_input_tokens`，如果一直是 0，就说明没命中。你项目里已经有 `prompt-cache-observation.ts` 在记录这个指标，可以直接看日志。

### 坑 4：压缩会重置缓存

OpenAI 文档明确写了：*"Summarization, compaction, or truncation can reset reuse."* 你的 `prepareStep` 里如果做消息压缩，压缩后的第一个请求前缀必然全新，要 100% 付写入价。

这是个取舍，不是错误：压缩让后面每一步输入变短，代价是压缩那一步缓存失效。**压缩的时机要尽量晚、尽量少、一次压到位**，不要每隔几步就压一点。

### 坑 5：并发请求拿不到缓存

Anthropic 文档：*"a cache entry only becomes available after the first response starts."* 如果你并行发 N 个请求想共享同一个前缀，它们会各自付写入价。要等第一个开始响应后再发其他的。对 Hue 的子 agent 设计这条很关键：父 agent 先发一个请求预热，子 agent 再并行启动。

### 坑 6：寿命从请求**开始**算，不是结束

文档原话：*"The lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response."* 一个流式输出 4 分钟的响应，结束时 5 分钟寿命只剩 1 分钟。如果工具执行又很慢（比如网页深读 30 秒），下一步的请求可能已经过期。长任务考虑 1 小时 TTL（写入价 2 倍，但避免反复重写）。

### 坑 7：断点放错位置

文档列为常见错误：*"Breakpoint on content that changes every request."* 断点要放在**最后一个跨请求保持不变的块**上，不要放在带时间戳或用户新消息的块上。你的 `decoratePromptCache` 的做法（system 第一条加断点，加一个稳定历史位置）方向是对的。

还有一个细节：`@ai-sdk/anthropic` 里有 `MAX_CACHE_BREAKPOINTS` 限制，超过会**忽略多余的断点并发 warning**，不会报错。

## 四、对缓存友好的配置清单

**应该固定的（整个 session 不动）：**
1. `tools` 的集合、名字、描述、参数 schema
2. 工具顺序（用 `toolOrder`）
3. `instructions` 的静态部分
4. `reasoning` / `effort` / `thinking` 配置
5. `model`

**应该放在末尾的（动态内容）：**
- 当前时间、用户个性化信息、检索到的内容
- 这类内容放在 messages 末尾而不是 system，因为 system 变了会连带 messages 缓存一起失效

**要小心的操作：**
- 删除历史消息、改写历史消息、压缩
- 图片：在任何位置增删都会使 tools 和 system 缓存失效
- 在已有 user 消息里追加文本（OpenAI 的坑：应该追加新消息而不是延长旧消息，因为旧缓存的终点在消息内部）

**要监控的指标：**
- Anthropic：`cache_read_input_tokens`、`cache_creation_input_tokens`、`input_tokens`
- OpenAI：`cached_tokens`
- 命中率 = 读取 token ÷ 总输入 token

## 五、这对自己写 agent loop 意味着什么

这是一个会直接影响 Hue 设计的点。我对照了 `docs/packages/core.md`：

- **不变量 5（"一个 turn 内 instructions 与工具列表不变"）正是为了缓存**，设计方向是对的。
- 但 core 目前没有说**跨 turn** 也要稳定，实际上跨 turn 的稳定性更重要：缓存的收益主要来自"同一个 session 内多个 turn"。
- 你之前提到的 `DECIDE: instructions 能否在 turn 内变化`，缓存角度的答案是：**不允许**，动态内容应通过追加 user 或 tool 消息的方式注入，而不是改 system。
- 压缩（`ContextStrategy`）和缓存天然冲突。可以在设计里让压缩策略知道"当前缓存断点在哪"，只压断点之后的部分，或者接受一次性成本。
