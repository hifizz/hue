我去读 `streamStep` 的实现，它就是那个循环。

还差两块：工具是什么时候真正执行的（`flush` 部分），以及一个 step 结束后消息历史怎么续上。

循环在 `streamText` 里的递归函数 `streamStep` 中，不是 `while`。源码是 `ai@7.0.83` 的 `src/generate-text/stream-text.ts`，下面的行号都在这个文件里，除非另写文件名。

## 一、源码怎么写的

**入口。** `streamText()`（约 359 行）本身很薄：把参数整理好，`new DefaultStreamTextResult({...})`（约 782 行）后**同步返回**结果对象，不是 Promise。循环在这个类的构造函数里，作为一个 async 函数启动，最后调用 `streamStep({currentStep: 0})`（约 2597 行）。所以 `streamText` 一返回，模型请求就已经发出了。

**一个 step 的流水线**（`streamStep`，约 1895 到 2570 行）：

| 顺序 | 做什么 | 位置 |
|---|---|---|
| 1 | 起三个超时计时器：整步、首个 chunk、chunk 间隔 | 约 1900 到 1970 |
| 2 | 调你的 `prepareStep`，拿到本步覆盖项。`stepNumber` 就是 `recordedSteps.length` | 约 2003 |
| 3 | 按覆盖项算出本步的 model、工具、toolChoice、messages、instructions、providerOptions、调用参数 | 约 2018 到 2074 |
| 4 | `streamLanguageModelCall(...)` 真正向厂商发请求，外面包了 `retry`（`maxRetries` 默认 2） | 约 2086 |
| 5 | 用 `executeToolsFromStream` 包住模型流：**边收流边执行工具** | 约 2188 |
| 6 | 逐个 chunk 转发给外部，同时记下 `tool-call`、`tool-result` 和 finishReason、usage | 约 2260 到 2430 |
| 7 | 流结束时发 `finish-step`，等这一步被记入 `recordedSteps` | 约 2440 到 2475 |
| 8 | 判断要不要进入下一步 | 约 2540 到 2565 |

**步与步之间怎么接上。** 一步被记录时（约 1422 行）：

```ts
stepMessagesForNextStep = [...currentStepMessages, ...stepResponseMessages]
```

也就是"本步发出去的消息 + 本步产生的 assistant 消息和 tool 消息"，下一步就在这个基础上继续。无状态模型每次要重发整段对话，SDK 在这里帮你累积。你在 `prepareStep` 里返回 `messages`，会替换这个累积值并延续到后面的步骤，所以压缩上下文放在这里做。

**工具什么时候执行**（`execute-tools-from-stream.ts`）。收到 `tool-call` chunk 时只做登记：无效的跳过，没有 `execute` 的不登记，需要批准的发出批准请求后 `return`，不登记。等到收到 `model-call-end` 时，如果 finishReason 是 `stop` 或 `tool-calls`（`is-tool-execution-allowed-finish-reason.ts`），才用 `Promise.all` **并行**执行所有登记的工具。工具结果作为 `tool-result` 或 `tool-error` chunk 回到流里。

**续跑判断**（约 2540 行），三个条件同时成立才递归调用 `streamStep(currentStep + 1)`：

```ts
clientToolCalls.length === clientToolOutputs.length + deniedToolApprovalResponses.length
&& (clientToolCalls.length > 0 || pendingDeferredToolCalls.size > 0)
&& !(await isStopConditionMet({ stopConditions, steps: recordedSteps }))
```

否则发出 `finish`，关闭流。

## 二、一个我读之前没想到的点

源码里**没有一行显式写"finishReason 不是 tool-calls 就停"**。文档说的那几种自然停止，都是通过上面第一个条件（调用数等于输出数）间接实现的：

| 情形 | 为什么停 |
|---|---|
| 模型没调工具 | `clientToolCalls.length > 0` 不成立 |
| 工具没有 `execute` | 不会被登记，有调用没输出，数量对不上 |
| 工具需要用户批准 | 发批准请求后直接 `return`，同样没输出 |
| 输出撞上限（finishReason 为 `length`）且带着调用 | 不满足"允许执行"的 finishReason，工具没跑，没输出 |
| 工具 `execute` 报错 | **不停**：`tool-error` 也算输出（约 2400 行），模型会看到错误并继续 |

最后一行说明工具报错会被模型看到并重试，这会消耗你的 step 预算。

## 三、浓缩版说明

### `streamText(options)` 是什么

用一个**模型调用循环**完成"让模型自己调工具直到完成"。不用手写 `while (stop_reason === "tool_use")`。

### 主要参数

| 参数 | 作用 | 要点 |
|---|---|---|
| `model` | 用哪个模型 | `prepareStep` 可逐步换 |
| `system` / `instructions` | 系统提示 | `system` 是旧别名 |
| `messages` / `prompt` | 对话输入 | 二选一 |
| `tools` | 工具表：描述、参数 schema、可选 `execute` | 有 `execute` 才会自动执行并续跑 |
| `toolChoice` | `auto`、`none`、强制某工具 | 默认 `auto` |
| `activeTools` | 本次调用向模型暴露的工具名子集 | 空数组 = 一个都不暴露 |
| `stopWhen` | 保险丝，一个或一组条件，任一为真就停 | 默认 `isStepCount(1)`，也就是**调完工具不会把结果送回模型** |
| `prepareStep` | 每步前的钩子，可覆盖本步设置 | 返回 `undefined` = 沿用外层 |
| `maxOutputTokens` `reasoning` `temperature`… | 单次模型调用的生成参数 | 对**每一步**生效，`prepareStep` 可逐步改 |
| `abortSignal` | 外部取消 | 一路传给模型请求、工具和计时器 |
| `timeout` | `totalMs`、`stepMs`、`firstChunkMs`、`chunkMs`、`toolMs` | 与 `abortSignal` 合并 |
| `maxRetries` | 单次模型调用失败重试，默认 2 | 在 step 内部，不占 step 数 |
| `providerOptions` | 透传给厂商的私有参数 | 与顶层 `reasoning` 不合并，前者优先 |
| 回调 | `onChunk`、`onStepFinish`（别名 `onStepEnd`）、`onFinish`（别名 `onEnd`）、`onError`、`onAbort`、`onStart`、`onToolExecutionStart/End` | 取消走 `onAbort`，不走 `onError` |

### 返回值（同步返回的结果对象）

- **流**：`stream`（全部事件）、`textStream`、`toUIMessageStream()`、`toTextStreamResponse()`
- **Promise**（流结束后才 resolve）：`text`、`reasoningText`、`toolCalls`、`toolResults`、`finishReason`、`usage`（最后一步）、`totalUsage`（所有步累加）、`steps`、`response`、`responseMessages`
- `consumeStream()`：把流读完。route.ts 在 `after()` 里对它调用，目的是让请求结束后后台仍然完成并结算。

### 一个 step 的生命周期（伪代码）

```ts
streamStep(n):
  r = await prepareStep({ steps, stepNumber: n, messages, ... })
  tools_n = filterActiveTools(tools, r.activeTools ?? activeTools)
  stream  = retry(() => model.stream({ tools_n, toolChoice, messages_n, ...settings_n }))
  for chunk of executeToolsFromStream(stream):       // 收到 model-call-end 才并行执行工具
      转发 chunk；记录 tool-call / tool-result / finishReason / usage
  记录 step；下一步 messages = 本步输入 + assistant 消息 + tool 消息
  if (调用数 == 输出数  &&  调用数>0 或有待回结果  &&  !stopWhen(steps))
      streamStep(n + 1)
  else
      发出 finish
```

### 停止条件速查

| 触发 | 结果 |
|---|---|
| 模型说完，没有工具调用 | 停 |
| 有调用没执行（无 `execute`、需批准、finishReason 是 `length`） | 停，等外部处理 |
| `stopWhen` 命中 | 停，即使模型还想调工具 |
| `abortSignal` 或超时 | 触发 `onAbort`，结果 Promise 以取消原因 reject |
| 工具报错 | 不停，错误作为 `tool-error` 回给模型 |
| 模型请求失败，重试用完 | 流里出现 `error` chunk，不是 throw |

### 对你代码的直接影响

1. `stopWhen: isStepCount(20)` 是**恰好等于 20 才停**（`steps.length === stepCount`）。
2. `prepareStep` 的 `stepNumber` 从 0 开始，所以你写的 `>= RESEARCH_MAX_STEPS - 1` 对应第 20 步，这一步会把 `activeTools` 过滤成空，模型只能输出文字。我读了 `filter-active-tools.ts`：`activeTools` 不是 `null` 就按名字过滤，空数组得到空对象。至于厂商那一层收到空 `tools` 时的行为，我没有读。
3. 每个 step 都会重发整段 messages。20 步的研究循环成本随步数增长，所以 `maxOutputTokens` 和 step 上限要一起考虑。
