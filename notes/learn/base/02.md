先说结论：**AI SDK 不会帮你自动重试，你得自己写。** 而且它在这种情况下的默认行为对你有利，但容易被误解，下面分开讲。

## 一、截断的 tool call 在 SDK 里会怎样

我读了源码，链路是这样的：

1. 模型生成工具参数（一段 JSON 字符串）时撞到 `max_tokens`，流被切断。
2. 这一步的 `finishReason` 变成 `'length'`（Anthropic 的 `max_tokens` 映射成它）。
3. `execute-tools-from-stream.ts:204` 的判断是：
   ```ts
   if (!isToolExecutionAllowedFinishReason(chunk.finishReason)) return
   ```
   而 `isToolExecutionAllowedFinishReason` 只放行 `'stop'` 和 `'tool-calls'`。所以 **`'length'` 时，工具一律不执行**。这就是 SDK 替你挡住"拿残缺参数去执行"的那一道保险。
4. 循环也不会继续，因为没有工具结果可送回去，整个 `streamText` 就以 `finishReason === 'length'` 结束。

所以问题不在"残缺的调用会被执行"，而在：**用户看到的是一个戛然而止的回答，没有任何提示。** 你需要自己检测并处理。

## 二、怎么检测

`streamText` 的结果对象有 `finishReason`（Promise）和 `steps`（Promise）。你的 route.ts 已经有 `onEnd` 回调，最简单的检测点在那里，但"重试"需要重新发起 `streamText`，所以通常放在**一个包装函数**里。

判断条件有两个层次：

```ts
const reason = await result.finishReason          // 'length' 表示撞到上限
const steps = await result.steps
const lastStep = steps.at(-1)
// 被截断时有没有一个残缺的工具调用，我读 SDK 源码时没找到专门的标记字段，
// 所以这里用 finishReason === 'length' 作为统一信号，不去区分是文字截断还是工具参数截断
```

注意我没有找到 SDK 暴露"被截断的是工具调用"的专门字段。`finishReason === 'length'` 只告诉你"撞上限了"。是截断在文字中间，还是截断在工具参数中间，要看 `lastStep.toolCalls` 和 `lastStep.text`。这个区分我没有实际跑过，下面代码里不依赖它。

## 三、最小可用的写法：整步重试

思路：撞 `length` → 把 `maxOutputTokens` 翻倍 → **重新发起同一个请求**（messages 不变）。因为被截断的那一步没有执行工具，也没有产生要保留的状态，所以整步重来是安全的。

```ts
import { streamText, type ModelMessage } from "ai"

const MODEL_MAX = 128_000          // 来自模型能力表，别硬编码，这里仅示意
const GROW = 2

async function streamWithGrowingLimit(
  opts: Parameters<typeof streamText>[0],
  startLimit: number,
) {
  let limit = startLimit
  for (;;) {
    const result = streamText({ ...opts, maxOutputTokens: limit })

    // 必须先消费流，finishReason 才会 resolve
    // 如果要边流边给前端，不能在这里等；见下面"流式的难点"
    const reason = await result.finishReason
    if (reason !== "length" || limit >= MODEL_MAX) return result

    limit = Math.min(limit * GROW, MODEL_MAX)
  }
}
```

这段代码能工作，但**有一个你必须知道的难点**。

## 四、流式的难点（这才是真正麻烦的地方）

你的 route.ts 是边生成边推给前端的（`toUIMessageStream`）。上面的写法要等 `finishReason` 才能判断是否重试，意味着：

- 用户已经看到了被截断的那半截文字。
- 重试后又会从头流一遍，前端会看到内容重复或被覆盖。

有三种应对方式，成本不同：

| 做法 | 怎么做 | 代价 |
|---|---|---|
| **A. 不重试，只提示** | `onEnd` 里发现 `length`，往流里写一条 data part，前端显示"回答被截断，点此继续" | 最简单，用户自己决定。推荐先做这个 |
| **B. 事先给足上限** | 按 effort 动态算：`high` 以上用 32k/64k，不让它容易撞到 | 零新增逻辑，但不能保证 |
| **C. 缓冲后重试** | 先不推给前端，等一步结束确认没撞 `length` 再放行 | 失去流式体验，延迟高，不建议 |

要真正在服务端透明重试且不让用户看到半截，只有 C。折中办法是**只对"工具调用被截断"的情况重试**：这种情况下模型在输出工具参数，前端本来就没有文字可看（SDK 的 `tool-input-delta` 只给 UI 展示参数构造进度），重复展示的代价小。

## 五、用 `prepareStep` 在一个 step 里提前预防

比起事后重试，更便宜的办法是**让每一步都有余量**：

```ts
prepareStep: ({ stepNumber, steps }) => {
  const last = steps.at(-1)
  // 上一步撞到了上限，说明这个任务输出偏长，这一步放宽
  if (last?.finishReason === "length") {
    return { maxOutputTokens: Math.min(MAX_OUTPUT_TOKENS * 2, MODEL_MAX) }
  }
  return undefined
}
```

但要看清楚这个的局限：**撞了 `length` 之后，循环本身已经停了**（上面第 3 点说的，没有工具结果可送回去），所以 `prepareStep` 根本没有机会在"下一步"生效。它只对"上一步没撞、下一步可能撞"的预防有用，不能用来救已经撞了的那一步。我这里的写法需要你理解这一点，否则会以为它能自动续跑。

## 六、续写（continue）和重试是两回事

Anthropic 文档提到另一种处理 `max_tokens` 的办法：**续写**。把被截断的 assistant 内容原样放回 messages，让模型接着往下写。这只适用于**文字被截断**的情况，不适用于工具参数被截断（残缺的 JSON 无法"接着写"，文档要求这种情况必须调大上限后重新生成）。

另外，如果开着 thinking，续写时 thinking 块要**原样**传回（Anthropic 文档要求带 signature、不能改），拼接不当会 400。这块我没有实测，如果你要做续写，我建议单独验证。

## 我的建议

对你现在的项目，按成本从低到高：

1. **先做 A**：在 `onEnd`（或 `result.finishReason`）里检测 `'length'`，写一条 data part 给前端，让 UI 提示"被截断"。几行代码，没有重复内容问题。
2. **再做 B**：把 `MAX_OUTPUT_TOKENS = 16_000` 这个固定值，改成按 `reasoning` 档位和模型能力来取，高档位给 32k 以上。你的 thread-chat 路径已经在做这件事（`generationSettings`），legacy-chat 这条路径是固定的。
3. **最后才考虑重试**，而且只针对"工具调用被截断"。
